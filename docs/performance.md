# 성능과 대량 처리

[← README로 돌아가기](../README.md)

Codex 추론 강도, 동시 실행, 부하·장시간 검증 결과를 모았습니다.

## Codex가 느리다면 — 추론 강도부터 확인하세요

`openai-subscription`에서 첫 글자까지 20~40초씩 걸린다면, 대개 원인은 하나입니다: **Codex가 답하기 전에 추론에 시간을 씁니다.** 그리고 그 시간은 프롬프트 성격에 따라 크게 출렁입니다.

실측(같은 provider·같은 조건, 12회씩):

| 프롬프트 | 첫 글자까지 중앙값 | 최대 | 편차 |
|---|---|---|---|
| "1+1은?" | 5.0초 | 6.3초 | 1.7배 |
| "세 가지를 기억해둬" | **18.0초** | **42.3초** | **7배** |

같은 조건에서 Claude는 2.9초와 2.8초로 **거의 차이가 없습니다.** 즉 이건 Codex 특유의 성질입니다.

`reasoningEffort`로 조절할 수 있습니다:

```ts
const runner = createAiRunner({
  provider: 'openai-subscription',
  defaultReasoningEffort: 'none',   // 호출마다 바꾸려면 run({ reasoningEffort })
});
```

| 설정 | 첫 글자까지 중앙값 | 최대 |
|---|---|---|
| 지정 안 함 | 23.1초 | 28.3초 |
| **`'none'`** | **5.6초** | **6.8초** |

**4배 빨라지고 편차도 5.7배 → 1.4배로 줄어듭니다.**

### 다만 어떤 작업이냐가 전부입니다

위 수치는 **세션에서 첫 글자가 나올 때까지**를 잰 것이고, 복잡한 프롬프트 기준입니다. 작업 성격을 바꿔 다시 재보니 효과가 크게 갈렸습니다(2026-09-24, 총 442회).

| 작업 | `'low'`의 효과 | 판단 |
|---|---|---|
| 웹 검색·도구를 쓰는 조사 (60~200초) | 시간 **30~48% 감소**, 품질 유지 | **쓰세요** |
| 짧은 분류·추출 (약 6초) | 시간 **1~9% 감소** | 얻을 게 없습니다 |
| 짧은 논리·계산 (약 6초) | 시간 5%, `'none'`은 **정답률 붕괴** | **기본값을 두세요** |

핵심은 **"생각할 게 많은 작업"이 아니라 "실제로 오래 걸리는 작업"**이라는 점입니다. 다이얼은 생각하는 시간만 줄이므로, 원래 6초 걸리는 작업에는 줄일 것이 없습니다.

`'none'`의 위험도 실측했습니다 — 조건 8개짜리 순서 퍼즐·반복문 추적·재귀 계산에서 **12회 중 0회 정답**이었습니다(같은 조건에서 `'low'`는 10/12). 분류·추출은 `'none'`에서도 만점이었으니, **다단계 추론이 섞이는지**가 갈림길입니다.

값은 `'none' | 'low' | 'medium' | 'high' | 'xhigh' | 'max'`입니다. 지정하지 않으면 Codex 기본값(medium)으로 돕니다 — `'medium'`을 명시하는 것과 결과가 같았습니다(시간 0.98배·근거 0.96배).

> ⚠️ **`reasoningEffort`를 지정하면 세션이 빠른 경로를 쓰지 않습니다.** `codex app-server`가 이 파라미터를 받지 않고 **조용히 무시하는 걸** 확인했기 때문입니다(말이 안 되는 값을 보내도 통과시킵니다). 지정한 옵션이 아무 효과 없이 사라지는 것보다 낫다고 보고, 실제로 적용되는 공식 SDK 경로를 쓰게 했습니다. 역설적으로 그게 더 빠릅니다 — 글자 단위 스트리밍을 잃는 대신 추론 시간을 훨씬 크게 줄이기 때문입니다.
>
> 참고로 `@openai/codex-sdk`의 타입에는 `'minimal'`이 있지만 `gpt-5.6-luna`는 이 값을 거부하고, 타입에 **없는** `'none'`이 실제로 지원됩니다. SDK 타입이 서버와 어긋나 있어서, llm-runner는 실측으로 확인한 값만 받습니다.

## 대량 배치로 돌릴 때 (수십~수백 건 처리)

문서를 수백 건 분석하는 배치를 만든다면, **세션은 답이 아닙니다.** 각 건이 서로 독립적이어야 하니 세션으로 묶으면 안 되고(맥락이 섞임), `run()`을 순서대로 부르면 건당 5~6초가 그대로 쌓입니다.

실제로 재보니 **답은 동시 실행**이었습니다. 5건씩 동시에 돌렸을 때:

| provider | 순차 1건 | 동시 5건(각각) | 처리량 |
|---|---|---|---|
| `claude-subscription` | 5.7초 | 9.4초 | **약 3.0배** |
| `openai-subscription` | 5.6초 | 6.3초 | **약 4.4배** |

동시 실행하면 건당 시간은 늘지만 전체 처리량은 크게 좋아집니다. 그리고 **Codex 쪽이 동시 실행을 훨씬 잘 견딥니다**(건당 5.6→6.3초로 거의 안 늘어남). 구독으로 배치를 돌려야 한다면 이 차이를 고려하세요.

```ts
// 예: 5건씩 묶어서 처리
for (const batch of chunk(documents, 5)) {
  const results = await Promise.all(batch.map((doc) => runner.run({ prompt: build(doc) })));
  // ...
}
```

동시 실행 수를 계속 올린다고 계속 빨라지지는 않습니다(위 표에서도 5배가 아니라 3~4.4배). 그리고 구독은 사용량 제한이 있으니, 정말 큰 배치라면 애초에 API 키 provider가 맞습니다.

### 누수 걱정 없이 오래 돌려도 되나

구독 provider는 호출마다 자식 프로세스를 띄우기 때문에, 오래 돌리면 프로세스나 파일 핸들이 쌓일 수 있다는 의심이 자연스럽습니다. 그래서 부하 테스트를 만들어 직접 확인했습니다:

```bash
node scripts/load-test.mjs claude-subscription   # 저장소를 클론했다면
```

각 provider당 105회 호출(순차 40 + 스트림 중도 포기 25 + 한 세션 25턴 + 동시 5건×3라운드)을 8분간 돌린 결과, **두 provider 모두 실패 0건, 프로세스 누수 0건, 파일 핸들 누수 0건**이었고 응답 시간도 뒤로 갈수록 느려지지 않았습니다(변화 ±0.7초 이내). 스트림을 첫 글자에서 끊고 버리는 경우에도 프로세스가 남지 않는 것까지 확인했습니다.

> 다만 정직하게 말하면 이건 **8분·105회 규모**입니다. 몇 시간짜리 배치나 수천 건 규모에서도 같은지는 아직 확인하지 않았습니다.

### 오래 열어두는 세션은 괜찮나 (상담봇처럼 뜸하게 오가는 경우)

사용자가 답을 읽고 몇 분 뒤에 다음 질문을 보내는 동안 세션이 끊기지 않는지는, 호출을 많이 한다고 확인되지 않습니다. 그래서 시간을 길게 끄는 테스트를 따로 만들었습니다:

```bash
node scripts/longevity-test.mjs claude-subscription
```

세션을 60초 → 120초 → 180초씩 방치한 뒤 매번 이전 맥락을 물어본 결과, **두 provider 모두 3분 방치 후에도 세션과 맥락이 살아있었고 재연결 지연도 없었습니다**(방치 후 응답 시간이 연속 호출 때와 동일). 400자 답변을 8턴 누적시켰을 때도 응답 시간이 느려지지 않았고 첫 턴 내용을 그대로 기억했습니다.
